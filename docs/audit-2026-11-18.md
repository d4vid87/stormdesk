# StormDesk production code and performance audit

November 18, 2026 · v4.12.0 baseline audit and validated local fixes

**Follow-up status:** All 16 findings were fixed and validated locally before release preparation for v4.12.1. The original audit below records the pre-fix baseline; implementation and validation are recorded at the end. Publication was authorized separately after validation.

**What this repo does:** StormDesk combines station observations, weather forecasts, alerts, history and the external HookEcho radar in a plain JavaScript dashboard. A Rust host optionally collects observations and stores them in SQLite; the hosted web app runs without that host. The expected load reviewed here is one owner plus several household screens, a continuously reporting station and an archive that can grow to several years.

**Verdict:** Fix data isolation and ingestion failures first, alongside the reproduced server-worker starvation. There are **16 actionable findings: 6 High, 8 Medium and 2 Low**, with no Critical finding established. Existing tests pass, but several test fixtures miss real protocol shapes or overlapping operations. The most substantial measured performance problem is concurrent cold history summaries: four clients delayed an unrelated request by **7.17–7.81 seconds**. No application source was changed, no commit was made and nothing was deployed.

## Architecture and critical paths

| Boundary | Actual implementation and important work |
| --- | --- |
| Full browser application | `site/` uses HTML, CSS and ES modules with direct DOM updates. There is no React/Vue renderer or frontend npm bundler. The startup graph check finds 44 eager modules. `boot.js` wires services; `app.js` owns local settings, navigation, notifications and the named scheduler. |
| Weather processing | HTTP providers in `api.js` and provider/context modules normalize data. Tempest WebSocket and local SSE/UDP deliver SI observation tuples. `desk.js` overlays station readings, retains context-keyed last-good data, and emits `wd:*` events. `pro.js` batches live display updates; Forecast Desk/Balanced Desk render forecast and supporting cards. |
| Alerts | Browser rules consume observations/forecasts and retain history, holds and latches. Native/server alert processing runs separately and must not be stopped merely because a display is hidden. |
| Native app | Rust 2021 and Tauri 2, with the same embedded site. Desktop has local collection, HTTP services, archive and integrations. Android compiles out the LAN server/storage modules and depends on cloud or remote-host data. |
| Headless/Docker | The Rust crate builds with `--no-default-features`, avoiding GTK/WebKit. Docker persists `WD_DATA_DIR` and needs host networking for UDP broadcast reception. |
| Station persistence | UDP, push and polling providers normalize into observations and additional sensor channels. Station fingerprints select separate SQLite files. WAL, a timestamp primary key, exclusion notes/indexes and transactional counter updates are present. Backfill has station-generation checks. Raw observations remain the source of truth. |
| HTTP concurrency | Four ordinary workers, two bounded upload workers and two queued bodies, eight SSE slots and four download permits. Some upstream cache fills already use single-flight/nonblocking behavior. Other slow work still occupies ordinary workers; see findings 6 and 15. |
| History | History modules load on first use. Bounded raw ranges feed canvas charts and accessible tables. Persistent daily-summary caches avoid repeat aggregation, with invalidation on changes; concurrent cold builders remain problematic. |
| Radar | StormDesk creates/unloads cross-origin `app.hookecho.io` iframes, validates camera messages and manages a snapshot fallback. HookEcho owns decoding, tiles, playback and GPU rendering. Those internal costs cannot be inferred from StormDesk's DOM. |
| Delivery | `site/` deploys to Cloudflare Pages project `stormdesk` at app.mystormdesk.com. `marketing/` is a different static site at mystormdesk.com. GitHub Actions builds Linux x86/ARM packages, Windows installers, universal macOS packages, Android APKs and headless/container releases. |

The main performance-sensitive paths are observation/event fanout, canvas/animation work, historical query and chart preparation, blocking provider fetches, cache rebuilding, and per-client configuration synchronization. Framework reconciliation is not a relevant diagnosis for this codebase.

### Optimizations that already work

Named jobs replace old timers and avoid overlapping returned promises. Visible-only jobs, hidden-document scheduling, bounded request/ETag/retry caches, last-good weather provenance, lazy History/home modules, batched current-value rendering, reused chart preparation and cached clock formatters already exist. The new layout controller moves original DOM nodes and skips unchanged ordering. Do not replace these with another framework or duplicate cache layer.

Normal radar navigation/visibility cleanup is covered by a 100-cycle fixture with zero retained observers and unloaded hidden iframes. Upload isolation is also effective: stalled uploads no longer consume the four ordinary workers. Findings below identify missing lifecycle transitions and other worker consumers, rather than repeating the resolved November 17 audit.

The service worker caches public shell assets only, excludes APIs/authorized/private responses, handles storage failure and revalidates code. Offline availability is opportunistic rather than an atomic pre-cached release; no new cache defect was established.

Browser measurements use isolated Chromium profiles, a loopback server and a temporary copy of the actual app seeded by the existing demo helper: 10 forecast days, 72 hourly rows and 336 history rows. Instrumentation observes long tasks, render measures, DOM activity and OS process counters.

Cold means a fresh browser profile. Warm means a second navigation with the same profile, retaining HTTP cache and last-good weather. The test server provides a 60-second asset cache; it is not a Cloudflare network simulation. “First useful weather” is the first animation frame after a forecast event with forecast cards mounted, not a standardized TTI metric or first live-provider reading.

## Must fix

### 1. Configured Tempest drops genuine UDP packets

- Category: correctness/reliability. Severity: **High**. Confidence: **complete source trace + official wire-format validation**; no physical hub exercised.
- Locations: [src-tauri/src/server.rs:150](/home/dwm/stormdesk/src-tauri/src/server.rs:150) `accepts_udp`, especially157–161; `listen_udp`1544; fixture2235.
- The configured numeric deviceId is compared to `packet["device_id"]`. Actual Tempest UDP messages carry `serial_number`/`hub_sn`, not REST/WebSocket device_id. A normal configured station therefore rejects every real obs_st, rapid_wind, lightning, rain and status packet. With no selection packets may be accepted, but `archive_accepts` cannot bind an identity of none. The existing unit tests invent device_id on UDP packets and pass.
- Impact: local live feed and minute archive stop, even though cloud WebSocket can mask the display failure; headless local collection loses its reason to exist. Backfill also needs an existing oldest row to start, so a fresh archive can remain empty.
- Smallest safe recommendation: resolve/persist selected device serial from station metadata and validate serial_number (and selected hub for hub_status), preserving rejection of other hubs. Do not remove identity filtering.
- Regression: official obs_st/rapid_wind/status fixtures without device_id from the selected serial must reach /udp and archive; foreign serials and post-switch delayed packets must not. Include ephemeral-port UDP integration, not only synthetic function fixtures.
- Primary protocol: https://weatherflow.github.io/Tempest/api/udp/v171/ (obs_st example lines135–142, rapid_wind60–65).

### 2. Station switching leaves the old live feed subscribed

**Confidence:** Reproduced socket lifetime failure with actual `signals.js` executed in isolated Node VM; saved-profile workflow established by complete call trace.

**Location:** [site/js/signals.js:140](/home/dwm/stormdesk/site/js/signals.js:140) (`connectWs`), `:158-174` (message/retry handlers), `:179-182` (`disconnectWs`); [site/js/boot.js:1022](/home/dwm/stormdesk/site/js/boot.js:1022) (`switchStation`), `:1361-1368` (`wd:refresh`); [site/js/app.js:678](/home/dwm/stormdesk/site/js/app.js:678) (`refreshAll`).

**Trigger/result:** Connect Tempest A, then select a saved Tempest B. `switchStation` saves B and calls `refreshAll`, which only starts new HTTP reads; nothing reconnects the socket captured with A's `deviceId`. A's full observations continue to be emitted without source identity, and `api.js:322` labels them with the *current* settings context, so they can overlay B's forecast. The ordinary Settings Save path is also broken when changing to a non-Tempest source: it clears token/device (boot605-609), then `initSignals` calls `connectWs`, which returns before closing the old socket. Reproduced A's socket still open and dispatching `wd:ws-obs` after WLL selection.

There is also an uncancellable retry: `onclose` schedules `setTimeout(connectWs, backoff)` without storing its handle. After `disconnectWs()` the queued callback reopens a socket because `connectWs()` sets `wantOpen=true`. Reproduced explicitly. Repeated close/manual reconnect can create avoidable churn (not claiming unlimited simultaneous sockets because connectWs closes its predecessor).

**Smallest recommendation:** Centralize connection ownership keyed by source/token/device identity; reconcile it on station identity changes (including config pulls and saved profiles). Close/detach before any early return, cancel pending reconnects on stop/reconfigure, and guard messages/retry callbacks by connection identity. Preserve normal hidden-page collection/alerts; this is identity cleanup, not blanket background suspension.

**Regression:** Real-source VM/socket test in `repro-data.cjs`. Extend with saved A→B switch expecting the next `listen_start.device_id` to be B, A late messages ignored, non-Tempest switch leaving zero sockets, and queued reconnect after stop creating zero sockets. Existing `check-station-switch` covers rollback and lookup races, not subscription ownership.

### 3. Nearby station names enter the page as HTML

**Confidence:** Complete input-to-sink trace plus reproduced raw markup at the sink. Browser JavaScript execution and a live provider's acceptance of attacker-created station names were not exercised.

**Location:** [site/js/signals.js:62](/home/dwm/stormdesk/site/js/signals.js:62), `:82-99` (`refreshSignals`); [src-tauri/tauri.conf.json:12](/home/dwm/stormdesk/src-tauri/tauri.conf.json:12) (`csp:null`).

**Trigger/result:** A nearby WeatherFlow response's `station_name` / `location_name`, NWS-discovered name or saved nearbyMetar name is passed to `label(r)` and interpolated directly into `innerHTML`. Fixture `station_name='<img src=x onerror="globalThis.pwned=1">'` survives as an element/event attribute in the HTML string passed to both station tables. No escaping or textContent boundary is present. A malicious or compromised upstream value could run in the application origin, exposing accessible local settings/credentials. Do not claim confirmed upstream exploitation; the dangerous trust-boundary handling itself is proven. Tauri explicitly has no CSP backstop in checked-in config.

**Smallest recommendation:** Build name/id/error fields with textContent or the existing shared escaping conventions. Do not solve only one field while leaving ids in HTML attributes unvalidated. Keep safe formatting for the fixed distance label separate from untrusted text. A CSP could be extra defense but is not a substitute and needs compatibility work.

**Regression:** `repro-data.cjs` confirms raw HTML sink. Browser fixture should return names with `<img>`, quotes and ampersands; assert exact visible text, zero generated images/event handlers and no marker execution. No need to contact or modify an external station.

### 4. Ingestion acknowledges failed archive writes

- Category: reliability/data loss. Severity: **High**. Confidence: **reproduced through actual HTTP + SQLite**.
- Locations: [src-tauri/src/ingest.rs:544](/home/dwm/stormdesk/src-tauri/src/ingest.rs:544) `accept`, especially571–580; `take_for_station:487–495`; `store_observation_channels:523`.
- `take` returns false both for a harmless throttled duplicate and for an archive write failure. `accept` ignores it and returns200. A temp SQLite BEFORE INSERT trigger raising ABORT produced HTTP200/body`success`, zero archive rows and `/diag` `archive write failed`. Disk full/IO/locking failures take this same error path.
- Impact: consoles receive an acknowledgement for an observation not stored and cannot distinguish a retryable host failure from an accepted sample.
- Smallest safe recommendation: distinguish Stored/Skipped/Failed at the ingest boundary; return a retryable5xx for failure, preserve200 for intentional throttling/duplicates. Keep atomic observation/counter commit.
- Regression: isolated DB failure after valid parsed report yields5xx, unchanged counters/no broadcast; retry after removing fault stores one observation; throttled report still200.
- Repro: `/tmp/stormdesk-audit-20261118/repro.py`; uses private temp config/DB, no upstream calls; output `FAILED_WRITE HTTP 200 BODY success ROWS 0`.

### 5. Settings synchronization loses edits and regresses revisions

- Category: correctness / reliability. Severity **High**. Confidence **reproduced** using actual production functions with deterministic deferred network responses.
- Locations: [site/js/boot.js:101](/home/dwm/stormdesk/site/js/boot.js:101) `pullConfig()`, specifically 102–113 and 120–121; [site/js/boot.js:183](/home/dwm/stormdesk/site/js/boot.js:183) settings listener, especially184; config revision listener198–201. Related write concurrency boundary149–172.
- What this is: a LAN/native household client fetches settings when another client broadcasts a configuration revision, then merges the returned shared settings locally.
- Concrete problem: `syncing=true` is held for the whole network request. Any user settings event during this wait is ignored by the pending-write collector. The response then overwrites the user edit. A second pull is allowed simultaneously and has no request sequence or monotonic revision check, so delayed revision3 can overwrite an already-applied revision4.
- Repro: production `pullConfig`, settings listener and `saveSettings` semantics were evaluated in Node VM. Start a deferred GET with station A/imperial; locally select B/metric; pendingSettings stays empty; return A/imperial revision2; final local state reverts to A/imperial. A separate test starts two pulls and resolves revision4 before3; final state and `rev` become3. Command: `node /tmp/stormdesk-audit-20261118/frontend-repro.mjs`.
- Impact: a slow LAN, reconnect, or overlapping household writes can silently undo a station, unit, alert-rule or other shared preference edit. This is not a hypothetical micro-optimization. Device-local theme/layout keys are filtered from pulls, so those particular values are not overwritten.
- Smallest recommendation: suppress settings echo only while synchronously applying the remote patch, keep user patches while a GET runs, apply remote results only for the latest request/non-older revision, and overlay pending local patches. Serialize the config-write drain instead of allowing independent concurrent PUTs. Preserve the existing revision-conflict merge and device-local filtering.
- Regression: deferred GET + local edits must retain/queue the edits; two out-of-order GETs must not regress revision/state; two overlapping saves with a409 conflict must converge on the newest local keys without a broadcast write loop. Extend existing station-switch tests with the real sync implementation, not just mocked pushConfig.
- If skipped: users can think a preference was saved while the screen/server silently returns to an earlier choice.

### 6. Concurrent cold history summaries occupy all ordinary workers

- Category: performance/reliability. Severity: **High** for multi-screen households with a large archive. Confidence: **reproduced using the shipped v4.12.0 release binary and isolated5-year archive**.
- Locations: [src-tauri/src/store.rs:230](/home/dwm/stormdesk/src-tauri/src/store.rs:230) `daily_head_json`, fallback273–290; [src-tauri/src/server.rs:1146](/home/dwm/stormdesk/src-tauri/src/server.rs:1146) daily route,1452–1496 worker pool.

Use a bounded rebuild worker if needed; retain all insertion/edit/exclusion invalidation rules. Do not simply put a blocking mutex around the query, which still parks every HTTP worker.

### 8. Delayed observations replace newer readings

**Confidence:** Reproduced `overlayStation` directly with actual API module; interval-history duplication established by source trace.

### 16. Archive endpoint lookup performs an avoidable full scan

- Category: performance/maintainability. Severity: **Low**. Confidence: **reproduced query plans and repeated timings**.

## Recommended implementation sequence

1. Protect source identity end-to-end: findings 1, 2, 7 and 8. Preserve collection and alert evaluation when displays are hidden; avoid a global “pause everything” optimization.
2. Close the trust/persistence/sync gaps: findings 3, 4 and 5. Keep credential validation, strict input handling, transactional counters, revision conflict handling and device-local preferences.
3. Address measured server delays: finding 6 first, then 15 and the small query change in 16. Reuse existing bounded caches and single-flight patterns; keep ordinary workers responsive instead of parking them behind a new mutex.
4. Correct time/date/history semantics: findings 9–12. Historical day boundaries need a deliberate timezone/cache migration, while the AQI fix can reuse the existing timestamp helper.
5. Reconcile presentation lifecycle in 14 and remove invisible work in 13. Preserve visible Observatory/Sky Theater artwork. Before broader animation changes, profile native WebKit and hardware-accelerated Chromium paint/layer costs on a representative low-power device.

No UI redesign, framework migration, generalized worker pool, downsampling policy or new dependency is justified merely by this audit. The source-scoped recommendations above solve demonstrated problems at their existing ownership boundaries.
